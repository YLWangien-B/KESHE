# 1 需求分析

## 1.1 问题描述

大型医院科室多，患者常常不知道该挂哪个科；热门科室号源紧张，排队等候时间长。
本系统要解决三件事：

1. **不知道挂哪个科** —— 按患者的症状推荐科室；
2. **不知道能不能挂上** —— 在线预约并实时显示剩余号源；
3. **不知道怎么走** —— 给出从一处诊室到另一处诊室的步行路线。

## 1.2 功能需求

| 6 | 路线查询 | 起点房间号、终点房间号 | 途经节点序列、总距离、换层次数 | 邻接矩阵图 + Floyd 算法 |

### 1.2.2 功能 7：候诊队列的详细设计

题目把它列为扩展要求，但队列是课程的重点内容，因此本项目把它当作**基本功能**实现。

**业务过程**：患者到院后先签到，进入其接诊医生的队伍并拿到排队号；
医生看完一位就叫下一位；叫到的人没来记一次过号，过号满两次重新排到队尾；
看完病才离开队列。患者随时能知道自己前面还有几个人。

**队列元素只记四样**：

```cpp
struct Waiting {
  int patient;      // 患者下标 —— 姓名从这里查
  int doctor;       // 接诊医生下标 —— 诊室从这里查
  int queueNo;      // 排队号，同一医生内从 1 开始递增
  int calledCount;  // 已叫号次数：0 未叫，1 已叫，≥2 过号
};
```

姓名、诊室、科室这些**都不重复保存**，需要时通过下标去查。这样数据只有一份，
不会出现「队列里的名字和患者表里的名字不一致」这种问题。

**队列的组织方式**：全院共用一条环形队列，靠 `doctor` 字段区分是哪个诊室的队伍。

> 为什么不是「每位医生一条队列」：医生有 64 位，若每人开一条 32 位置的队列，
> 光是队列数组就要 64 × 32 × 16 字节 = 32 KB，而绝大多数队伍长期是空的。
> 共用一条 64 位置的队列只占 1 KB，既省空间，又能直接按就诊顺序查看全院候诊情况。

**环形队列用在这里的好处**：入队、出队都是 O(1)。出队腾出的数组位置会被后面的
患者循环使用——正是「叫走一个、进来一个」的候诊场景。

### 1.2.3 扩展功能（本阶段只给设计思路，不写代码）

| 编号 | 功能 | 设计思路 | 该用的数据结构与算法 |
| --- | --- | --- | --- |
| E1 | 症状的权重评定与自由文本导诊 | 患者直接输入一句话（如「最近胸口发闷还有点咳嗽」），系统自动切出症状词并算出匹配程度 | **症状词典 + 正向最长匹配**：从左到右扫描，在每个位置尝试匹配词典中最长的词，命中就跳过该词。现在的功能 1 只需要患者勾选症状，这一步留作扩展 |
| E2 | 停诊通知 | 医生停诊时，遍历该医生该时段的预约，给每位患者写一条通知 | 顺序表 + 由「医生+日期+时段」直接定位排班槽，再扫描预约表 |
| E3 | 患者评价 | 就诊后给医生打分，评分参与导诊排序 | 顺序表 + 增量平均（`Doctor` 里的 `rankSum` / `rankCount` 两个字段已经留好，O(1) 更新） |
| E4 | 转诊推荐 | 某科室号满时，推荐症状谱相近的科室 | 把每个科室的症状集合看成集合，用 **Jaccard 相似度** `\|A∩B\| / \|A∪B\|` 衡量相近程度；集合很小（每科 ≤ 8 个症状），用布尔数组求交并即可 |

这些扩展功能都**不影响主干的数据结构选型**，作为答辩时的加分内容。

### 1.3.3 容量设计

数据结构的容量必须在编译期确定，所以先按业务上界定容量，再留余量：

| 表 | 依据 | 容量 |
| --- | --- | --- |
| 科室 | 要求 ≥ 10，留余量 | 16 |
| 医生 | 要求 ≥ 30，留余量 | 64 |
| 患者 | 演示规模 | 128 |
| 预约记录 | 演示规模 | 256 |
| 症状 | 覆盖常见症状 | 64 |
| 房间 | 4 层 × 12 间 + 余量 | 64 |
| 路网节点 | 4 层 × 20 个节点号 | 128 |
| 排班槽 | 医生 × 7 天 × 4 时段 | 64×7×4 |

数据总库体积约 60 KB，用 `static_assert` 把上界钉住。

**一个容易踩的坑**：默认线程栈只有 1 MB。总库虽然不大，但为了将来加表也不出问题，
统一用「函数内静态对象」持有（放在静态存储区），不作为局部变量。

## 1.5 用户界面设计

课程要求里提到「以图形化界面展示科室分布、医生排班和预约状态」，同时说明
「不能使用类库、模板等（**用户界面除外**）」，即界面部分允许用现成的库。

考虑到课程设计的重心是数据结构与算法，本阶段采用**字符界面**，
把精力放在数据结构与算法本身。字符界面同样能完整演示全部六项功能。

### 1.5.1 界面形态

```
================ 医院门诊预约与智能导诊系统 ================
  1. 智能导诊     按症状推荐科室
  2. 医生查询     按科室 / 职称 / 擅长领域查询
  3. 在线预约     选医生与时段，生成预约凭证
  4. 预约管理     查看与取消本人的预约
  5. 排班展示     查看医生一周排班与余号
  6. 就诊路线     查询两个诊室之间的走法
  0. 退出
============================================================
请选择：
```

### 1.5.2 字符界面的三个要点

1. **中英混排对齐**。终端里一个汉字占两格、一个 ASCII 字符占一格，而 `printf` 的
   `%-12s` 是按**字节数**补齐的，中文列必然参差不齐。做法是先算出字符串的显示宽度
   （`ui.h` 的 `width` 函数），再手工补空格。
2. **中文编码**。源码与数据文件统一用 UTF-8，程序启动时把控制台代码页也切成 UTF-8。
   注意不能用 `system("chcp 65001")`：`system` 会另起一个 `cmd.exe`，
   它会把父进程继承来的标准输入重定向（如 `hospital.exe < in.txt`）消费掉，
   导致随后读不到任何输入，表现为「菜单一闪而过」。
3. **输入容错**。菜单输入非数字不退出、编号查不到给明确提示、
   两点不连通时说明原因，不让程序崩掉。

## 1.6 需求到设计的对应关系

```
智能导诊 ──┬─ 症状勾选（将来可扩展为文本分词）
           ├─ 带权二部图：一侧症状、一侧科室，边权是关联强度
           └─ 邻域加权求和 + 按得分排序

在线预约 ──┬─ 排班槽用三维数组存，下标即主键，查找 O(1)
           └─ 版本号校验「检查余量 -> 扣减」，防止超卖

路线查询 ──┬─ 把全部房间与通道编成一张节点表，用邻接矩阵存边
           └─ Floyd 一次算出任意两点最短距离，之后查询是 O(1) 查表

排班展示 ──── 三维数组按医生与日期枚举
预约管理 ──── 顺序表遍历 + 按患者筛选
医生查询 ──── 顺序表遍历 + 按科室 / 职称 / 擅长领域匹配
```

各模块的职责与调用关系见 [03-程序结构设计.md](03-程序结构设计.md)。

# 2 数据结构与算法

本章逐个说明系统用到的数据结构：**存什么 → 为什么这样存 → 关键操作与复杂度**。

| 数据结构 | 文件位置 | 用在哪 |
| --- | --- | --- |
| 顺序表 `SeqList<T, N>` | `ds.h` | 科室、医生、患者、预约、房间等全部数据表 |
| 环形队列 `RingQueue<T, N>` | `ds.h` | 候诊队列 |
| 散列表 `HashMap` | `ds.h` | 编号 / 名字到表内下标的索引 |
| 二维数组 `ScheduleTable<日期, 时段>` | `ds.h` | 医生排班 |
| 带权图 `WeightedGraph` | `ds.h` | 就诊路网（邻接矩阵 + Floyd） |
| 带权二部图 `BipartiteGraph` | `ds.h` | 症状与科室的关联关系 |

设计原则四条：

1. **容量编译期确定**。全部表的容量由业务上界推出，写成常量，运行期不申请内存。
2. **下标就是主键**。能用下标直接定位的（排班、路网、二部图顶点）就不另外建索引。
3. **按访问方式选结构**。按编号查一次 → 散列表；整体遍历和排序 → 顺序表；
   关系型数据 → 图；有先后次序 → 队列。
4. **关系存放在结构里，不塞进记录**。症状与科室的关联放在二部图中、
   排班放在二维数组中，实体记录里只留必要的字段，避免同一个关系在两处各存一份。

## 2.1 顺序表 `SeqList<T, N>`

**存储结构**：静态数组 + 实际长度。

```cpp
template <typename T, int N>
class SeqList {
  T data_[N];
  int n_ = 0;
};
```

**用途**：科室表、医生表、患者表、预约表、房间表、症状表都用它。

**为什么用顺序表**：这几张表的访问方式是「整体遍历 + 按下标随机访问 + 偶尔排序」，
顺序表在这三项上都是最优的，内存连续、缓存友好。插入都发生在表尾（装载阶段），
删除很少（只有删预约记录），规模几十到几百，元素移动的代价可以忽略。

**关键操作**：

| 操作 | 复杂度 | 说明 |
| --- | --- | --- |
| 按下标访问 `[i]` | O(1) | |
| 尾部追加 `push` | O(1) | 容量满返回 -1，由调用者处理 |
| 按下标删除 `removeAt` | O(n) | 后面的元素依次前移 |

**模板的用法说明**：元素类型和容量作为模板参数给出，这样顺序表只写一份，
不必为每种元素类型复制一遍代码。模板是 C++ 的语言特性，不属于「类库」。
答辩时如果被问到，可以指出：这恰恰是「同一套逻辑复用在不同数据上」，
而不是「调用了别人写好的容器」。

## 2.2 环形队列 `RingQueue<T, N>`

**存储结构**：静态数组 + 队首下标 + 队尾下标 + 元素个数。

```cpp
template <typename T, int N>
class RingQueue {
  T data_[N];
  int head_ = 0, tail_ = 0, n_ = 0;
};
```

**为什么不用顺序表凑合**：顺序表也能当队列用，但出队要移动元素（O(n)）；
更关键的是，队列**表达的是「先进先出」这个约束**，用独立的类型能把这个约束
摆在代码里，而不是靠调用者自觉。

**入队出队的过程**（容量 4）：

```
入 1,2,3               出 1                  入 4
┌───┬───┬───┬───┐    ┌───┬───┬───┬───┐    ┌───┬───┬───┬───┐
│ 1 │ 2 │ 3 │   │    │   │ 2 │ 3 │   │    │ 4 │ 2 │ 3 │   │
└───┴───┴───┴───┘    └───┴───┴───┴───┘    └───┴───┴───┴───┘
  ↑head       ↑tail     head↑   ↑tail      tail↑ head↑
                                          （队尾回绕到数组开头）
```

**关键操作**：入队、出队都是 O(1)。`tail = (tail + 1) % N` 实现回绕。

除了基本的入队出队，还提供两个辅助操作，供候诊队列使用：

| 操作 | 说明 | 复杂度 |
| --- | --- | --- |
| `at(i)`（可写） | 取队内第 i 个元素的可写引用，用于就地修改（如把「已叫号次数」加一） | O(1) |
| `removeAt(i)` | 删除队内第 i 个元素（患者看完病离开队列），用「逐个出队再放回」保留其余元素的相对次序 | O(n) |

**用途**：功能 7 候诊队列。全院共用一条 64 位置的队列，靠 `doctor` 字段区分队伍；
患者签到入队拿排队号，医生叫号、过号、就诊完成离开队列。
队内元素只存「患者下标、医生下标、排队号、已叫号次数」四样，
姓名与诊室通过下标去查，不重复保存。

**环形队列加的三个操作**：候诊除了入队出队，还需要这几件事，因此给 `RingQueue`
补了三个方法（都不是新结构，只是把数组的既有能力开出来）：

| 方法 | 用途 | 复杂度 |
| --- | --- | --- |
| `at(i)` 可写版 | 就地改队内元素（把「已叫号次数」加一），省去来回搬运 | O(1) |
| `removeAt(i)` | 删除队内第 i 个（患者看完病离开），逐个出队再放回以保留次序 | O(n) |
| — | 位置查询 `positionOf` / `waitingAhead` / `countOf` 由业务层遍历实现 | O(n) |

**「先来先看」这条规则怎么守住**（这是候诊队列最容易做错的地方）：

被叫号的人不立刻出队，而是留在队里、把 `calledCount` 加一，理由有两个：
患者要能看到「已经叫到我了」；真正离开队列应当是「看完病」这个动作。

但这样一来，队首就可能出现一个「叫过但没走」的人。此时**不能越过他去叫后面的人**，
否则队列就退化成无序的了。所以 `callNext` 遇到这种情况返回 `QUEUE_FIRST_CALLED`，
由医生决定：继续等，或者用 `pass()` 把他记为过号；记满 `kMaxPass` 次后他重新排到队尾，
队列继续往前走。这样既不会让不守时的人一直堵着队伍，也不会让后来的人插队。

**「前面还有几人」要只数还没被叫号的**：正在诊室里的那几位不算在「前面等的人」里，
否则患者会以为还要等很久。所以显示时用 `waitingAhead()` 而不是排队号之差。

## 2.3 散列表 `HashMap`

**存储结构**：**链地址法**。一个桶数组，每个桶挂一条同义词链。

```cpp
constexpr int kHashBuckets = 211;   // 取质数，减少冲突

struct HashNode {
  char key[16];    // 编号，如 "K01"、"D1"、"RA101"
  int  value;      // 数据表里的下标
  int  next;       // 同义词链的下一个结点
};

class HashMap {
  HashNode node_[1024];
  int head_[kHashBuckets];
  int nodeCount_;
};
```

**为什么需要散列表**：系统里到处都要「按编号找一个东西」——
医生报房间号要查房间、排班表引用医生编号要查医生、用户输入 `K01` 要查科室。
若用顺序表线性查找，每次都是 O(n)；用散列表是 O(1)。

**散列函数**：把字符串每个字符累加，再对桶数取余。

```
K01 → h = ((0*31 + 'K')*31 + '0')*31 + '1' = 76346
      76346 % 211 = 175  →  挂在 175 号桶上
```

桶数取**质数 211**，是为了让取余的结果分布更均匀。

**冲突处理与查找**：

```
   桶 174: 空
   桶 175: ──► ["K01", 0] ──► ["K15", 14] ──► -1
   桶 176: 空
```

查找时先算桶号，再顺着这条链比较字符串。因为散列值相同的键都挂在同一条链上，
所以链不会漏掉任何一个键。

**为什么用链地址法，不用开放定址法**：开放定址法在删除元素时会截断探测链，
必须额外做「重插入」修补；链地址法删除只要调整链指针，实现更直观。
本系统的插入都集中在装载阶段，删除只在运行期偶尔发生，用链地址法更省事。

**关键操作复杂度**：

| 操作 | 平均 | 最坏（全部冲突） |
| --- | --- | --- |
| 插入 / 查找 | O(1) | O(n) |

**用途**：

| 索引 | 键 → 值 |
| --- | --- |
| `deptIndex` | 科室编号 → 科室下标 |
| `doctorIndex` | 医生编号 → 医生下标 |
| `patientIndex` | 患者编号 → 患者下标 |
| `roomIndex` | 房间号 → 房间下标 |

## 2.4 带权图 `WeightedGraph`（邻接矩阵 + Floyd 算法）

这是本系统里最重要的一种结构，路线查询全靠它。

### 2.4.1 模型

把医院里的**每个房间当成图的一个顶点**，两个房间之间**能直接走过去就画一条边**，
边上的权值是距离（米）。

值得注意的是：**电梯口和楼梯口也登记为房间**，所以它们天然就是图上的顶点，
不需要为「上下楼」再发明一套特殊规则。整张图因此是一张普通的无向带权图。

```
门诊楼1层（楼层 0）                        节点号
  ┌────┬────┬────┬────┬────┬────┬────┐
  │电梯│101 │102 │103 │104 │105 │106 │ 楼梯
  │ 0  │ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │  7
  └─┬──┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┘
    │10   │10  │10  │10  │10  │10  │10        同一层相邻房间距离 10 米
    │     │    │    │    │    │    │
    │20   │    │    │    │    │    │  20      电梯/楼梯连通上下层，距离 20 米
    │     │    │    │    │    │    │
  ┌─┴──┬──┴─┬──┴─┬──┴─┬──┴─┬──┴─┬──┴─┐
  │电梯│201 │202 │203 │204 │205 │206 │ 楼梯      门诊楼2层（楼层 1）
  │ 20 │ 21 │ 22 │ 23 │ 24 │ 25 │ 26 │  27
  └────┴────┴────┴────┴────┴────┴────┘
```

**节点编号规则**：`节点号 = 楼层号 × 20 + 房间号`。
这样节点号与「楼层-房间」一一对应，从房间名就能算出节点号，反过来也能算回去。

### 2.4.2 存储：邻接矩阵

```cpp
class WeightedGraph {
  static constexpr int kMaxNodes = 128;
  static constexpr int kInf = 100000000;   // 「不可达」
  int dist_[kMaxNodes][kMaxNodes];         // 距离矩阵
  int next_[kMaxNodes][kMaxNodes];         // 路径还原用
  int n_;
};
```

`dist_[i][j]` 存放 i 到 j 的距离；不相邻（或还没算过）时存 `kInf`。
对角线 `dist_[i][i] = 0`。无向图，所以矩阵是对称的。

**为什么用邻接矩阵，不用邻接表**：

| | 邻接矩阵 | 邻接表 |
| --- | --- | --- |
| 空间 | O(V²) | O(V+E) |
| 判断两点是否相邻 | O(1) | O(deg) |
| 配合 Floyd 使用 | 直接就是 Floyd 要的形式 | 要先转换 |

本系统 V = 128（全部楼层加起来），矩阵 128×128 个 int ≈ 64 KB，空间完全不是问题。
而且**Floyd 算法本身就是在矩阵上跑的**，用邻接矩阵可以把存储和算法直接对上，代码最短。
换成邻接表反而要额外做一次转换。

### 2.4.3 算法：Floyd 求任意两点最短路

**核心思想**：`dist[i][j]` 先只看「i 和 j 直接相连」的情况；
然后逐轮放宽「允许经过哪些中转点」——第 k 轮允许经过编号 ≤ k 的顶点，
每轮尝试用 k 作为中转点，看能不能把 i 到 j 的距离缩短。

```cpp
void floyd() {
  // 初始化 next：能直达就从 i 走到 j
  for (i, j) next_[i][j] = (dist_[i][j] < kInf && i != j) ? j : -1;

  for (int k = 0; k < n_; ++k)        // 中转点
    for (int i = 0; i < n_; ++i)      // 起点
      for (int j = 0; j < n_; ++j)    // 终点
        if (dist_[i][k] + dist_[k][j] < dist_[i][j]) {
          dist_[i][j] = dist_[i][k] + dist_[k][j];   // 用 k 中转更近
          next_[i][j] = next_[i][k];                 // 记下走法
        }
}
```

`next_[i][j]` 记录「从 i 去 j 的下一步该走到哪个节点」，用来还原整条路线：

```cpp
int buildPath(int u, int v, int* path, int cap) {
  int n = 0, cur = u;
  while (cur != -1) {
    path[n++] = cur;
    if (cur == v) return n;
    cur = next_[cur][v];     // 顺着 next 一路走下去
  }
}
```

**复杂度**：三重循环，O(V³) = 128³ ≈ 200 万次比较，实测几毫秒。
之后每次查询只是查一次表，O(1)。

**为什么用 Floyd 而不是 Dijkstra**：

| | Floyd | Dijkstra（每个起点跑一次） |
| --- | --- | --- |
| 一次算出的结果 | **任意两点**之间的最短路 | 单个起点到所有点的最短路 |
| 复杂度 | O(V³) | O(V²) 或 O(E log V) |
| 查询 | O(1) 查表 | 要重新算 |

路线查询是患者反复使用的功能，而且路网是**固定不变**的（房间和走廊不会变）。
所以「一次算好、以后查表」的 Floyd 非常合适：预计算 200 万次，换来每次查询 O(1)。

如果医院要扩建、路网经常变，那就该用 Dijkstra 每次现算（或者只重算受影响的部分）。
这是一个典型的「按使用场景选算法」的例子。

### 2.4.4 边长是怎么定的

| 相连的两个房间 | 距离 | 理由 |
| --- | --- | --- |
| 同一层相邻诊室 | 10 米 | 沿走廊走一间房的宽度 |
| 本层走廊两端（电梯口 ↔ 楼梯口） | 30 米 | 走廊全长 |
| 电梯口 ↔ 相邻层电梯口 | 20 米 | 等电梯 + 乘梯的等效距离 |
| 楼梯口 ↔ 相邻层楼梯口 | 20 米 | 上下楼一层的等效距离 |

这些数值写在数据文件 `layout.txt` 里，改数据就能改路线结果，不用改代码。

## 2.5 排班表：二维数组 `ScheduleTable<日期, 时段>`

题目实现提示第 3 条要求排班用**二维数组**、按日期和时段索引。做法是
**每位医生一张二维表**，两个下标就是主键：

```cpp
// ds.h
template <int Days, int Slots>
class ScheduleTable {
  ScheduleSlot slot_[Days][Slots];
  ...
};

// model.h —— 排班表放在医生记录里，就是「每位医生一张排班表」
struct Doctor {
  ...
  ScheduleTable<kMaxDay, kMaxSlot> schedule;  // 7 天 × 4 个时段
};

// 按「日期 + 时段」直接定位，O(1)
ScheduleSlot& s = h.slot(doctor, day, slot);
```

**为什么是二维而不是三维**：三维数组 `[医生][日期][时段]` 把所有医生的排班堆在
一个大块里，容量要按「医生上限 × 7 × 4」预留（64×7×4 = 1792 个格子，每个格子
16 字节，约 28 KB）；而「每位医生一张二维表」只在医生记录里放 7×4 = 28 个格子，
按实际医生数分配，医生上限调大也不会成倍浪费空间。两个下标仍然恰好是主键，
查找还是一次下标运算。

**为什么不用顺序表 + 散列表索引**：用顺序表存的话，「按医生和日期查排班」要么线性
扫描，要么再建一个复合键散列表；而二维数组**下标本身就是主键**，不需要索引，
也不会有「表的顺序和下标公式对不上」这类问题（这正是开发过程中真实踩过的坑）。

**未使用的格子**用 `assigned` 标记区分，这样「该时段没排班」和
「该时段排班了但号源为 0」两种状态不会混淆。

**预约时的并发安全**（题目实现提示第 4 条：预约时检查并扣减剩余号源）：
号源的「检查余量 → 扣减」发生在一次函数调用里连着的三步，中间不会被打断：

```cpp
ScheduleSlot& s = h.slot(doctor, day, slot);
if (s.stopped) return;                // 1. 停诊检查
if (s.quota - s.booked <= 0) return;  // 2. 余量检查
++s.booked;                           // 3. 扣减
s.version = ++h.versionClock;         //    并取一个新版本号
```

槽里还带一个 `version`（版本号）。任何号源变动都会把版本号换成时钟的下一个值，
于是「此前看到的余号信息」立刻作废 —— 拿着旧版本去扣减会被拒绝并要求重选。
这样即使将来把程序改成多线程、或者接入网络请求，也不会出现超卖。

## 2.6 算法一：智能导诊

### 2.6.1 数学模型：带权二部图 `BipartiteGraph`

按题目实现提示第 1 条，把「症状—科室」的关联关系建成一张**带权二部图**
G = (S ∪ K, E, W)：

* 一侧是**症状**顶点集 S（25 个）；
* 另一侧是**科室**顶点集 K（12 个）；
* 一条边 e = (s, k) 表示「出现症状 s 时应当考虑科室 k」，**边权** W(s,k) ∈ [1,5]
  表示这种指向的强度。

```
   症状侧                边权                科室侧
  ┌────────┐          ┌──────┐          ┌────────────┐
  │  胸闷  │──────────│  3   │──────────│  心血管内科 │
  │        │──────────│  2   │──────┐   └────────────┘
  └────────┘          └──────┘      │
  ┌────────┐                        └──►┌────────────┐
  │  咳嗽  │──────────│  3   │──────────│  呼吸内科   │
  │        │──────────│  2   │──────┐   └────────────┘
  └────────┘          └──────┘      └──►┌────────────┐
  ┌────────┐                            │   儿科     │
  │  腹痛  │──────────│  3   │──────────│  消化内科   │
  └────────┘          └──────┘          └────────────┘
                         ...
```

**二部图的性质被用上了**：顶点分成互不相邻的两部分，边只存在于两部分之间，
所以两侧的顶点分开存、分开索引：

```cpp
char symptomName_[kMaxSymptoms][kMaxSymptomName];  // 症状侧顶点名
HashMap symptomIndex_;                             // 症状名 -> 症状顶点号
int deptCount_;                                    // 科室侧顶点数（科室下标即顶点号）
```

**邻接表用「前向星」而不是邻接矩阵**：边不多（31 条），而且需要「按顶点列出它的
所有邻居」。前向星用两个链头数组加一个边集就能做到，从两侧查各自的邻居都是 O(度)：

```cpp
int symptomHead_[kMaxSymptoms];   // 症状 -> 关联科室链的链头
int deptHead_[kMaxDepartments];   // 科室 -> 关联症状链的链头

struct Edge {
  int dept, symptom, weight;
  int deptNext;     // 科室侧链上的下一条边
  int symptomNext;  // 症状侧链上的下一条边
};
```

> 一处踩过的坑：一条边在边集中占**两个**结点，两侧各挂一次。一开始这两个结点只写了
> 一个 `next`，于是后建的科室链把先建的症状链覆盖掉了 —— 症状能查到科室，
> 科室却查不到症状。改成两个端点各有一个 `next` 才对。这是这类结构最容易写错的地方。

### 2.6.2 患者症状与科室描述的匹配

题目实现提示第 2 条要求「将患者症状与科室描述进行匹配」。做法是：
**科室的描述文本里写出它的常见症状词，匹配就是把这些词和患者说的话对上**。
分三步：

**第一步：从患者的话里找出症状词（词典驱动的正向最长匹配）**

从左到右扫描患者的输入，在每个位置拿**全部症状名和它们的同义词**去比，
取能匹配上的最长的那个，命中就跳过这个词，否则前进一个字节。

```
输入：最 近 胸 口 发 闷 ， 还 有 点 咳 嗽
                       ↑
        在「胸」处比出最长的同义词「胸口发闷」（12 字节）→ 命中症状「胸闷」
```

取最长而不是第一个命中的，是为了处理包含关系（如「胸口」与「胸口发闷」）。
还要处理**用词差异**：患者说的是口语，症状顶点用的是规范词，所以每个症状挂几个
同义词（「胸闷」← 胸口发闷 / 胸口闷；「发热」← 发烧 / 体温高）。

**第二步：沿二部图把症状的权重累加到科室**

```
score(k) = Σ W(s, k)        （s 取第一步命中的症状）
```

这是二部图上的一次**邻域加权求和**：从命中的症状顶点出发，沿边走到相邻的科室顶点，
把边权累加上去。

**第三步：回到科室描述核对，再排序**

患者用的是口语词时，回到该科室的描述里查一下这个词有没有出现：

* 描述里写了 → 说明这确实在该科室的主诉范围内，**按原权重计分**；
* 描述里没写 → 说明只是沾边，权重**打对折**。

这一步让「与科室描述匹配」真正落到描述文本上，而不只是走过边表。
最后按 score 从大到小排序取前几名，排序用**插入排序** —— 科室只有 12 个，
结果最多存 5 条，这个规模下插入排序最快也最好写。

**执行过程举例**：

```
输入：「最近胸口发闷，还有点咳嗽和头晕」
识别：胸闷(同义词，但描述里有「胸口发闷」→ 全额)  咳嗽(规范词)  头晕(规范词)

  科室        命中的症状与权重      得分
  心血管内科  胸闷:3                3
  呼吸内科    咳嗽:3                3
  神经内科    头晕:3                3
  儿科        咳嗽:2                2
```

排第一位的是心血管内科，与患者最先说的「胸口发闷」一致。

```
输入：「孩子发烧还拉肚子」
识别：发热(同义词 → 儿科描述里有「发烧」→ 全额 3)
      腹泻(同义词 → 儿科描述里有「拉肚子」→ 全额 2)

  科室        得分
  儿科        5      ← 发烧 3 + 拉肚子 2
  消化内科    2
```

### 2.6.3 复杂度与设计说明

* 第一步：O(输入长度 × (症状数 + 同义词总数))，输入几十个字、词表几打，瞬间完成；
* 第二步：O(科室数 × 每科室症状数) = 12 × 4；
* 第三步：插入排序 O(科室数²) = 12² = 144。

**为什么同义词不和症状名并列成顶点**：同义词只是「同一个症状的另一种说法」，
如果各自成为顶点，二部图里就会出现多个其实指同一件事的顶点，权重被分散，
得分也就不再可解释。把同义词挂在症状顶点上，图的结构保持干净，识别时多认几个词即可。

**评分为什么不用百分比**：原始得分（如 5 分）比百分比更直观地反映「命中了几条、
强度多大」，患者看到「得分 5，依据：胸闷 气短」就明白为什么推荐这个科。

## 2.7 算法二：就诊路线

分两步：**建图**在装载阶段完成，**查询**在用户点击时完成。

### 2.7.1 建图（装载阶段）

```
第一步：读 layout.txt，把每个房间登记进 rooms 表，并记下它的路网节点号
        同时求出最大的节点号，用来确定图有多少个顶点
        → road.init(maxNode)

第二步：再读一遍 layout.txt，按每行的「相邻房间:距离」建边
        → road.addEdge(u, v, w)

第三步：调用 road.floyd()，一次算出所有点对的最短距离与走法
```

**为什么要读两遍**：第一遍读完才知道图一共有多少个顶点；
邻接矩阵要先确定大小才能初始化，边也才有地方放。
（如果用邻接表，顶点数是动态的，就可以一边读一边建——这是邻接表的优势之一。）

### 2.7.2 查询（用户点击时）

```cpp
RouteResult Route::between(const Hospital& h, int fromRoom, int toRoom) {
  int u = h.rooms[fromRoom].node;      // 起点房间对应的图顶点
  int v = h.rooms[toRoom].node;        // 终点房间对应的图顶点
  if (!h.road.reachable(u, v)) return 空结果;   // 不连通

  r.totalDistance = h.road.distance(u, v);     // O(1) 查表
  int n = h.road.buildPath(u, v, path, kMaxRouteSteps);   // 还原路线

  // 把节点号翻译回房间，并统计换层次数
  for (i...) r.steps[i] = h.findRoomByNode(path[i]);
  for (i...) if (楼层不同) ++r.floorChanges;
}
```

**复杂度**：查距离 O(1)，还原路径 O(路径长度)。整个过程与图的规模无关。

### 2.7.3 换层提示

路线上的换层发生在电梯口或楼梯口。判断依据是相邻两个节点的楼层号不同；
再按节点名字里有没有「电梯」两个字，判断患者用的是电梯还是楼梯，
输出「在『门诊楼1层电梯口』乘电梯，到达 4 层的『内科楼2层电梯口』」这样的指引。

### 2.7.4 执行过程举例（RA101 → RB209）

```
起点：RA101（门诊楼1层心血管内科诊室），节点号 1
终点：RB209（内科楼2层中医科诊室），  节点号 69

Floyd 已算出 dist[1][69] = 70，next 链给出走法：
  1  → 0（门诊楼1层电梯口，+10 米）
  0  → 60（内科楼2层电梯口，跨层 +20 米）
  60 → 67（内科楼2层楼梯口，+30 米）
  67 → 69（内科楼2层中医科诊室，+10 米）

合计 70 米，换层 1 次
```

## 2.8 数据结构与功能的对应总表

| 功能 | 数据结构 | 算法 | 复杂度 |
| --- | --- | --- | --- |
| 智能导诊 | **带权二部图**（症状与科室为顶点，关联强度为边权） | 正向最长匹配 + 邻域加权求和 + 插入排序 | O(句长 × 词表) + O(科室 × 症状) |
| 医生查询 | 顺序表 + 散列表 | 线性筛选 | O(医生数) |
| 在线预约 | **每位医生一张 日期×时段 二维数组** + 版本号 | 检查并扣减剩余号源的原子操作 | O(1) |
| 预约管理 | 顺序表 + 散列表 | 按患者遍历 | O(预约数) |
| 排班展示 | 二维数组 + 顺序表 | 按日期与时段枚举 | O(日期 × 时段) |
| 路线查询 | 带权图（邻接矩阵） | Floyd 预计算 + 查表 | 预计算 O(V³)，查询 O(1) |
| 候诊队列 | 环形队列 | 入队 / 出队 / 过号重排 | O(1)，按位删除 O(n) |
| *扩展* 停诊通知 | 顺序表 | 按槽位反查预约 | O(预约数) |
| *扩展* 患者评价 | 顺序表 | 增量平均 | O(1) |
| *扩展* 转诊推荐 | 集合（布尔数组） | Jaccard 相似度 | O(科室² × 症状) |

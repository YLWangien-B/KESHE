# 2 数据结构与算法

本章逐个说明系统用到的四种数据结构：**存什么 → 为什么这样存 → 关键操作与复杂度**。

设计原则三条：

1. **容量编译期确定**。全部表的容量由业务上界推出，写成常量，运行期不申请内存。
2. **下标就是主键**。能用下标直接定位的，就不另外建索引。
3. **按访问方式选结构**。按编号查一次 → 散列表；整体遍历和排序 → 顺序表；
   关系型数据 → 图；有先后次序 → 队列。

---

## 2.1 顺序表 `SeqList<T, N>`

**存储结构**：静态数组 + 实际长度。

```cpp
template <typename T, int N>
class SeqList {
  T data_[N];
  int n_ = 0;
};
```

**用途**：科室表、医生表、患者表、预约表、房间表、症状表都用它。

**为什么用顺序表**：这几张表的访问方式是「整体遍历 + 按下标随机访问 + 偶尔排序」，
顺序表在这三项上都是最优的，内存连续、缓存友好。插入都发生在表尾（装载阶段），
删除很少（只有删预约记录），规模几十到几百，元素移动的代价可以忽略。

**关键操作**：

| 操作 | 复杂度 | 说明 |
| --- | --- | --- |
| 按下标访问 `[i]` | O(1) | |
| 尾部追加 `push` | O(1) | 容量满返回 -1，由调用者处理 |
| 按下标删除 `removeAt` | O(n) | 后面的元素依次前移 |

**模板的用法说明**：元素类型和容量作为模板参数给出，这样顺序表只写一份，
不必为每种元素类型复制一遍代码。模板是 C++ 的语言特性，不属于「类库」。
答辩时如果被问到，可以指出：这恰恰是「同一套逻辑复用在不同数据上」，
而不是「调用了别人写好的容器」。

## 2.2 环形队列 `RingQueue<T, N>`

**存储结构**：静态数组 + 队首下标 + 队尾下标 + 元素个数。

```cpp
template <typename T, int N>
class RingQueue {
  T data_[N];
  int head_ = 0, tail_ = 0, n_ = 0;
};
```

**为什么不用顺序表凑合**：顺序表也能当队列用，但出队要移动元素（O(n)）；
更关键的是，队列**表达的是「先进先出」这个约束**，用独立的类型能把这个约束
摆在代码里，而不是靠调用者自觉。

**入队出队的过程**（容量 4）：

```
入 1,2,3               出 1                  入 4
┌───┬───┬───┬───┐    ┌───┬───┬───┬───┐    ┌───┬───┬───┬───┐
│ 1 │ 2 │ 3 │   │    │   │ 2 │ 3 │   │    │ 4 │ 2 │ 3 │   │
└───┴───┴───┴───┘    └───┴───┴───┴───┘    └───┴───┴───┴───┘
  ↑head       ↑tail     head↑   ↑tail      tail↑ head↑
                                          （队尾回绕到数组开头）
```

**关键操作**：入队、出队都是 O(1)。`tail = (tail + 1) % N` 实现回绕。

**用途**：本阶段代码里还没用到（六项基本功能不需要排队），
但 `ds.h` 里已经实现好，扩展功能 E1 候诊队列直接用它 —— 每位医生一条队列，
患者签到入队、叫号出队，过号则重新入队尾。

## 2.3 散列表 `HashMap`

**存储结构**：**链地址法**。一个桶数组，每个桶挂一条同义词链。

```cpp
constexpr int kHashBuckets = 211;   // 取质数，减少冲突

struct HashNode {
  char key[16];    // 编号，如 "K01"、"D1"、"RA101"
  int  value;      // 数据表里的下标
  int  next;       // 同义词链的下一个结点
};

class HashMap {
  HashNode node_[1024];
  int head_[kHashBuckets];
  int nodeCount_;
};
```

**为什么需要散列表**：系统里到处都要「按编号找一个东西」——
医生报房间号要查房间、排班表引用医生编号要查医生、用户输入 `K01` 要查科室。
若用顺序表线性查找，每次都是 O(n)；用散列表是 O(1)。

**散列函数**：把字符串每个字符累加，再对桶数取余。

```
K01 → h = ((0*31 + 'K')*31 + '0')*31 + '1' = 76346
      76346 % 211 = 175  →  挂在 175 号桶上
```

桶数取**质数 211**，是为了让取余的结果分布更均匀。

**冲突处理与查找**：

```
   桶 174: 空
   桶 175: ──► ["K01", 0] ──► ["K15", 14] ──► -1
   桶 176: 空
```

查找时先算桶号，再顺着这条链比较字符串。因为散列值相同的键都挂在同一条链上，
所以链不会漏掉任何一个键。

**为什么用链地址法，不用开放定址法**：开放定址法在删除元素时会截断探测链，
必须额外做「重插入」修补；链地址法删除只要调整链指针，实现更直观。
本系统的插入都集中在装载阶段，删除只在运行期偶尔发生，用链地址法更省事。

**关键操作复杂度**：

| 操作 | 平均 | 最坏（全部冲突） |
| --- | --- | --- |
| 插入 / 查找 | O(1) | O(n) |

**用途**：

| 索引 | 键 → 值 |
| --- | --- |
| `deptIndex` | 科室编号 → 科室下标 |
| `doctorIndex` | 医生编号 → 医生下标 |
| `patientIndex` | 患者编号 → 患者下标 |
| `roomIndex` | 房间号 → 房间下标 |

## 2.4 带权图 `RoadNet`（邻接矩阵 + Floyd 算法）

这是本系统里最重要的一种结构，路线查询全靠它。

### 2.4.1 模型

把医院里的**每个房间当成图的一个顶点**，两个房间之间**能直接走过去就画一条边**，
边上的权值是距离（米）。

值得注意的是：**电梯口和楼梯口也登记为房间**，所以它们天然就是图上的顶点，
不需要为「上下楼」再发明一套特殊规则。整张图因此是一张普通的无向带权图。

```
门诊楼1层（楼层 0）                        节点号
  ┌────┬────┬────┬────┬────┬────┬────┐
  │电梯│101 │102 │103 │104 │105 │106 │ 楼梯
  │ 0  │ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │  7
  └─┬──┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┴──┬─┘
    │10   │10  │10  │10  │10  │10  │10        同一层相邻房间距离 10 米
    │     │    │    │    │    │    │
    │20   │    │    │    │    │    │  20      电梯/楼梯连通上下层，距离 20 米
    │     │    │    │    │    │    │
  ┌─┴──┬──┴─┬──┴─┬──┴─┬──┴─┬──┴─┬──┴─┐
  │电梯│201 │202 │203 │204 │205 │206 │ 楼梯      门诊楼2层（楼层 1）
  │ 20 │ 21 │ 22 │ 23 │ 24 │ 25 │ 26 │  27
  └────┴────┴────┴────┴────┴────┴────┘
```

**节点编号规则**：`节点号 = 楼层号 × 20 + 房间号`。
这样节点号与「楼层-房间」一一对应，从房间名就能算出节点号，反过来也能算回去。

### 2.4.2 存储：邻接矩阵

```cpp
class RoadNet {
  static constexpr int kMaxNodes = 128;
  static constexpr int kInf = 100000000;   // 「不可达」
  int dist_[kMaxNodes][kMaxNodes];         // 距离矩阵
  int next_[kMaxNodes][kMaxNodes];         // 路径还原用
  int n_;
};
```

`dist_[i][j]` 存放 i 到 j 的距离；不相邻（或还没算过）时存 `kInf`。
对角线 `dist_[i][i] = 0`。无向图，所以矩阵是对称的。

**为什么用邻接矩阵，不用邻接表**：

| | 邻接矩阵 | 邻接表 |
| --- | --- | --- |
| 空间 | O(V²) | O(V+E) |
| 判断两点是否相邻 | O(1) | O(deg) |
| 配合 Floyd 使用 | 直接就是 Floyd 要的形式 | 要先转换 |

本系统 V = 128（全部楼层加起来），矩阵 128×128 个 int ≈ 64 KB，空间完全不是问题。
而且**Floyd 算法本身就是在矩阵上跑的**，用邻接矩阵可以把存储和算法直接对上，代码最短。
换成邻接表反而要额外做一次转换。

### 2.4.3 算法：Floyd 求任意两点最短路

**核心思想**：`dist[i][j]` 先只看「i 和 j 直接相连」的情况；
然后逐轮放宽「允许经过哪些中转点」——第 k 轮允许经过编号 ≤ k 的顶点，
每轮尝试用 k 作为中转点，看能不能把 i 到 j 的距离缩短。

```cpp
void floyd() {
  // 初始化 next：能直达就从 i 走到 j
  for (i, j) next_[i][j] = (dist_[i][j] < kInf && i != j) ? j : -1;

  for (int k = 0; k < n_; ++k)        // 中转点
    for (int i = 0; i < n_; ++i)      // 起点
      for (int j = 0; j < n_; ++j)    // 终点
        if (dist_[i][k] + dist_[k][j] < dist_[i][j]) {
          dist_[i][j] = dist_[i][k] + dist_[k][j];   // 用 k 中转更近
          next_[i][j] = next_[i][k];                 // 记下走法
        }
}
```

`next_[i][j]` 记录「从 i 去 j 的下一步该走到哪个节点」，用来还原整条路线：

```cpp
int buildPath(int u, int v, int* path, int cap) {
  int n = 0, cur = u;
  while (cur != -1) {
    path[n++] = cur;
    if (cur == v) return n;
    cur = next_[cur][v];     // 顺着 next 一路走下去
  }
}
```

**复杂度**：三重循环，O(V³) = 128³ ≈ 200 万次比较，实测几毫秒。
之后每次查询只是查一次表，O(1)。

**为什么用 Floyd 而不是 Dijkstra**：

| | Floyd | Dijkstra（每个起点跑一次） |
| --- | --- | --- |
| 一次算出的结果 | **任意两点**之间的最短路 | 单个起点到所有点的最短路 |
| 复杂度 | O(V³) | O(V²) 或 O(E log V) |
| 查询 | O(1) 查表 | 要重新算 |

路线查询是患者反复使用的功能，而且路网是**固定不变**的（房间和走廊不会变）。
所以「一次算好、以后查表」的 Floyd 非常合适：预计算 200 万次，换来每次查询 O(1)。

如果医院要扩建、路网经常变，那就该用 Dijkstra 每次现算（或者只重算受影响的部分）。
这是一个典型的「按使用场景选算法」的例子。

### 2.4.4 边长是怎么定的

| 相连的两个房间 | 距离 | 理由 |
| --- | --- | --- |
| 同一层相邻诊室 | 10 米 | 沿走廊走一间房的宽度 |
| 本层走廊两端（电梯口 ↔ 楼梯口） | 30 米 | 走廊全长 |
| 电梯口 ↔ 相邻层电梯口 | 20 米 | 等电梯 + 乘梯的等效距离 |
| 楼梯口 ↔ 相邻层楼梯口 | 20 米 | 上下楼一层的等效距离 |

这些数值写在数据文件 `layout.txt` 里，改数据就能改路线结果，不用改代码。

## 2.5 排班槽为什么用三维数组

排班槽的主键是「医生 × 日期 × 时段」，三者共同唯一确定一个格子。
最自然的存法就是三维数组：

```cpp
Schedule schedule[kMaxDoctor][kMaxDay][kMaxSlot];

// 按主键直接定位，O(1)
Schedule& s = h.slot(doctor, day, slot);
```

**为什么不用顺序表 + 散列表索引**：排班槽一共 64×7×4 = 1792 个格子（实际只用了 252 个）。
用顺序表存的话，「按医生和日期查排班」要么线性扫描，要么再建一个复合键散列表；
而三维数组**下标本身就是主键**，查找就是一次下标运算，不需要索引，也不会有
「表的顺序和下标公式对不上」这类问题（这正是开发过程中真实踩过的坑）。

代价是浪费一些空间（1792 - 252 个空格子），每个格子 24 字节，约 37 KB，可以接受。

**未使用的格子**用 `assigned` 标记区分，这样「该时段没排班」和
「该时段排班了但号源为 0」两种状态不会混淆。

## 2.6 算法一：智能导诊

### 2.6.1 数学模型：带权二部图

把「症状—科室」的关联关系建成一张**带权二部图**：

* 一侧是**症状**顶点（25 个）；
* 另一侧是**科室**顶点（12 个）；
* 一条边表示「出现这个症状时应当考虑这个科室」，**边上的权值**（1~3）
  表示这种指向的强度。

```
   症状侧                边权                科室侧
  ┌────────┐          ┌──────┐          ┌────────────┐
  │  胸闷  │──────────│  3   │──────────│  心血管内科 │
  │        │──────────│  2   │──────┐   └────────────┘
  └────────┘          └──────┘      │
  ┌────────┐                        └──►┌────────────┐
  │  咳嗽  │──────────│  3   │──────────│  呼吸内科   │
  │        │──────────│  2   │──────┐   └────────────┘
  └────────┘          └──────┘      └──►┌────────────┐
  ┌────────┐                            │   儿科     │
  │  腹痛  │──────────│  3   │──────────│  消化内科   │
  └────────┘          └──────┘          └────────────┘
                         ...
```

### 2.6.2 算法

患者勾选若干症状后，对每个科室把它**命中的**症状权重加起来：

```
score(科室) = Σ 权重(症状, 科室)      （只累加患者勾选了的症状）
```

这实际上是二部图上的一次**邻域加权求和**：从勾选的症状出发，
沿边走到相邻的科室，把边权累加到科室上。

然后按 score 从大到小排序，取前几名。排序用**插入排序**——科室只有 12 个，
而且结果最多存 5 条，插入排序在这个规模下最快也最好写。

**执行过程举例**（患者勾选「胸闷、咳嗽、气短」）：

| 科室 | 命中的症状与权重 | score |
| --- | --- | --- |
| 心血管内科 | 胸闷:3 + 气短:2 | **5** |
| 呼吸内科 | 咳嗽:3 + 气短:2 | **5** |
| 儿科 | 咳嗽:2 | 2 |
| 消化内科 | 0（三个症状都没关联） | 不入选 |

### 2.6.3 复杂度与设计说明

* 时间：O(科室数 × 每科室症状数) = 12 × 8，瞬间完成；
* 空间：O(科室数)。

**为什么做成「选症状」而不是「输入一句话」**：
选症状的实现最直接，也最容易讲清楚二部图是怎么用的。
自由文本输入需要额外一套分词（见扩展功能 E5 的正向最长匹配设计），
不影响二部图本身的用法，留作扩展。

**评分为什么不用百分比**：原始得分（如 5 分）比百分比更直观地反映
「命中了几条、强度多大」，患者看到「得分 5，依据：胸闷 气短」就明白为什么推荐这个科。

## 2.7 算法二：就诊路线

分两步：**建图**在装载阶段完成，**查询**在用户点击时完成。

### 2.7.1 建图（装载阶段）

```
第一步：读 layout.txt，把每个房间登记进 rooms 表，并记下它的路网节点号
        同时求出最大的节点号，用来确定图有多少个顶点
        → road.init(maxNode)

第二步：再读一遍 layout.txt，按每行的「相邻房间:距离」建边
        → road.addEdge(u, v, w)

第三步：调用 road.floyd()，一次算出所有点对的最短距离与走法
```

**为什么要读两遍**：第一遍读完才知道图一共有多少个顶点；
邻接矩阵要先确定大小才能初始化，边也才有地方放。
（如果用邻接表，顶点数是动态的，就可以一边读一边建——这是邻接表的优势之一。）

### 2.7.2 查询（用户点击时）

```cpp
RouteResult Route::between(const Hospital& h, int fromRoom, int toRoom) {
  int u = h.rooms[fromRoom].node;      // 起点房间对应的图顶点
  int v = h.rooms[toRoom].node;        // 终点房间对应的图顶点
  if (!h.road.reachable(u, v)) return 空结果;   // 不连通

  r.totalDistance = h.road.distance(u, v);     // O(1) 查表
  int n = h.road.buildPath(u, v, path, kMaxRouteSteps);   // 还原路线

  // 把节点号翻译回房间，并统计换层次数
  for (i...) r.steps[i] = h.findRoomByNode(path[i]);
  for (i...) if (楼层不同) ++r.floorChanges;
}
```

**复杂度**：查距离 O(1)，还原路径 O(路径长度)。整个过程与图的规模无关。

### 2.7.3 换层提示

路线上的换层发生在电梯口或楼梯口。判断依据是相邻两个节点的楼层号不同；
再按节点名字里有没有「电梯」两个字，判断患者用的是电梯还是楼梯，
输出「在『门诊楼1层电梯口』乘电梯，到达 4 层的『内科楼2层电梯口』」这样的指引。

### 2.7.4 执行过程举例（RA101 → RB209）

```
起点：RA101（门诊楼1层心血管内科诊室），节点号 1
终点：RB209（内科楼2层中医科诊室），  节点号 69

Floyd 已算出 dist[1][69] = 70，next 链给出走法：
  1  → 0（门诊楼1层电梯口，+10 米）
  0  → 60（内科楼2层电梯口，跨层 +20 米）
  60 → 67（内科楼2层楼梯口，+30 米）
  67 → 69（内科楼2层中医科诊室，+10 米）

合计 70 米，换层 1 次
```

## 2.8 数据结构与功能的对应总表

| 功能 | 数据结构 | 算法 | 复杂度 |
| --- | --- | --- | --- |
| 智能导诊 | 带权二部图（科室记录里存症状下标与权重） | 邻域加权求和 + 插入排序 | O(科室 × 症状) |
| 医生查询 | 顺序表 + 散列表 | 线性筛选 | O(医生数) |
| 在线预约 | 三维数组 + 版本号 | 版本校验的检查-扣减 | O(1) |
| 预约管理 | 顺序表 + 散列表 | 按患者遍历 | O(预约数) |
| 排班展示 | 三维数组 + 顺序表 | 按医生与日期枚举 | O(日期 × 时段) |
| 路线查询 | 邻接矩阵图 | Floyd 预计算 + 查表 | 预计算 O(V³)，查询 O(1) |
| *扩展* 候诊队列 | 环形队列 | 入队 / 出队 / 过号重排 | O(1) |
